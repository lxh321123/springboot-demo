## 一、MySQL 隔离级别与 MVCC

**1. MySQL 四种隔离级别分别是什么？英文全称和中文名各是什么？**

- **Read Uncommitted**（读未提交）：允许脏读。
- **Read Committed**（读已提交）：不允许脏读，但存在不可重复读和幻读 。
- **Repeatable Read**（可重复读）：不允许脏读、不可重复读，InnoDB 实现下基本解决幻读 。
- **Serializable**（串行化）：三种异常全部避免 。

**2. RC 和 RR 的全英文是什么？它们的中文名分别是什么？**

- **RC = Read Committed**，读已提交。
- **RR = Repeatable Read**，可重复读 。

**3. RC 和 RR 在快照读生成 Read View 的时机上有什么区别？**

- **RC**：每次执行 `SELECT` 都生成一个新的 Read View 。
- **RR**：事务启动后，第一次执行 `SELECT` 时生成 Read View，整个事务期间复用这一个 。

**4. 什么是快照读？什么是当前读？两者最核心的区别是什么？**

- **快照读**：读取的是历史版本数据，不加锁，普通 `SELECT` 就是快照读 。
- **当前读**：读取的是记录的最新版本，且读取时会加锁，保证其他事务不能同时修改 。
- 核心区别：**是否加锁**。快照读靠 MVCC 实现非阻塞读，当前读靠锁实现。

**5. 哪些 SQL 操作属于当前读？至少说出三种。**

- `SELECT ... FOR UPDATE`（排他锁）
- `SELECT ... LOCK IN SHARE MODE`（共享锁）
- `INSERT`、`UPDATE`、`DELETE` 

**6. MVCC 是什么？它主要解决什么问题？**

- MVCC = Multiversion Concurrency Control，多版本并发控制。
- 通过维护数据行的多个历史版本，实现**读写不互相阻塞**，解决读写冲突，提升并发性能 。

**7. MVCC 靠哪几个核心组件实现？Undo Log、Read View、隐藏字段分别起什么作用？**

- **Undo Log**：记录数据的历史版本，形成版本链 。
- **Read View**：定义“我能看到什么数据”，包含 `m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id` 四个关键字段，用于判断版本的可见性 。
- **隐藏字段**：每行记录有 `DB_TRX_ID`（最近修改该行的事务 ID）和 `DB_ROLL_PTR`（指向 Undo Log 的指针）。

**8. RR 级别下，快照读能完全避免幻读吗？为什么说“基本无幻读”而不是“绝对无幻读”？**

快照读在 RR 下能避免幻读，因为整个事务复用同一个 Read View，看不到其他事务新提交的新增行 。但“基本”是因为：如果事务中先做了快照读，然后又做了**当前读**（如 `UPDATE`），当前读会读到最新数据，后续再快照读就可能感知到幻影行 。

**9. 当前读靠什么机制防幻读？间隙锁和 Next-Key Lock 分别是什么？**

- 靠**间隙锁**和 **Next-Key Lock** 。
- **间隙锁**：锁住索引记录之间的“间隙”，阻止其他事务在间隙中插入新行 。
- **Next-Key Lock**：记录锁 + 间隙锁的组合，既锁住记录本身，也锁住记录前面的间隙 。

**10. 举个例子说明：当前读如何通过间隙锁阻止其他事务插入新行，从而避免幻读？**

事务 A 执行 `SELECT * FROM t WHERE id > 10 FOR UPDATE`，会锁住 `id > 10` 范围内的间隙。事务 B 想插入 `id = 15` 的新行，会被阻塞，直到事务 A 提交。这样事务 A 再查一次，结果集不会多出新行 。

**11. RC 和 RR 在加锁行为上有什么主要区别？**

- **RR**：支持间隙锁和 Next-Key Lock，范围查询会锁住间隙 。
- **RC**：**没有间隙锁**，只加记录锁，因此存在幻读问题 。
- 并发性上 RC 更好，因为锁范围更小 。

**12. 为什么很多互联网公司默认用 RC，而不是 RR？**

历史原因：MySQL 5.1.5 之前只有 STATEMENT 格式 binlog，RC + STATEMENT 会导致主从数据不一致，所以默认 RR。现在 binlog 默认 ROW 格式后这个限制已不存在，RC 因为**锁更少、并发更高**，被很多互联网公司采用 。


## 二、事务与锁基础

**13. 事务的 ACID 分别指什么？**

- **Atomicity**（原子性）：操作要么全部成功，要么全部回滚 。
- **Consistency**（一致性）：事务前后数据保持一致状态 。
- **Isolation**（隔离性）：并发事务之间互不干扰 。
- **Durability**（持久性）：提交后数据永久保存 。

**14. 脏读、不可重复读、幻读分别是什么？各由哪个隔离级别解决？**

- **脏读**：读到其他事务未提交的数据。**RC 及以上解决** 。
- **不可重复读**：同一事务两次读同一行，结果不同。**RR 及以上解决** 。
- **幻读**：同一事务两次范围查询，结果集行数不同。**Serializable 解决；RR 在快照读下通过 MVCC 解决，当前读通过间隙锁解决** 。

**15. InnoDB 有哪些锁类型？**

- **共享锁（S）**：允许读，阻止写 。
- **排他锁（X）**：允许读写，阻止其他所有锁 。
- **意向锁（IS/IX）**：表级锁，表示将要给行加 S 锁或 X 锁 。
- **记录锁（Record Lock）**：锁住索引记录 。
- **间隙锁（Gap Lock）**：锁住索引记录之间的间隙 。
- **Next-Key Lock**：记录锁 + 间隙锁 。
- **插入意向锁**：INSERT 前设置的间隙锁，表示插入意图 。

**16. 什么是死锁？InnoDB 怎么检测和处理死锁？**

- 死锁：多个事务互相持有对方需要的锁，都在等待，无法继续 。
- InnoDB 默认启用死锁检测，检测到后**回滚其中一个事务**（牺牲者）。
- 可以通过 `SHOW ENGINE INNODB STATUS` 查看最后一次死锁信息 。

**17. 乐观锁和悲观锁的区别是什么？分别适用什么场景？**

- **悲观锁**：假设冲突必然发生，先加锁再操作（如 `FOR UPDATE`）。适合写多读少、冲突激烈的场景。
- **乐观锁**：假设冲突较少，先操作，提交时检查版本号/CAS。适合读多写少、冲突较少的场景。

**18. `SELECT ... FOR UPDATE` 和 `SELECT ... LOCK IN SHARE MODE` 有什么区别？**

- `FOR UPDATE`：加**排他锁（X 锁）**，其他事务不能读也不能写 。
- `LOCK IN SHARE MODE`：加**共享锁（S 锁）**，其他事务可以读，但不能写 。


## 三、索引与 SQL 优化

**19. 什么是聚簇索引？什么是二级索引？回表是什么？**

- **聚簇索引**：叶子节点存储完整行数据，InnoDB 主键索引就是聚簇索引 。
- **二级索引**：叶子节点只存储索引列 + 主键值 。
- **回表**：通过二级索引找到主键后，再回聚簇索引查完整行数据 。

**20. 什么是最左前缀原则？联合索引 `(a, b, c)` 哪些查询能走索引？**

- 从联合索引最左列开始，依次匹配，中间不能断 。
- 能走索引：`a`、`a+b`、`a+b+c`、`a+c`（a 走索引，c 在索引中过滤但不走排序）。
- 不能走索引：`b`、`c`、`b+c` 。

**21. 索引失效的常见场景有哪些？至少说出五种。**

- 对索引列使用函数或表达式（`WHERE YEAR(created_at) = 2023`）。
- `LIKE '%xxx'` 以通配符开头 。
- 数据类型不匹配，发生隐式类型转换 。
- 使用 `OR` 且条件涉及不同索引列 。
- 索引选择性太低（重复值太多），优化器选择全表扫描 。

**22. `EXPLAIN` 里你最关注哪些字段？**

- **type**：访问类型，`ref`、`range` 较好，`ALL` 是全表扫描 。
- **key**：实际使用的索引。
- **rows**：预估扫描行数。
- **Extra**：`Using index` 表示覆盖索引，`Using filesort` 表示需要额外排序 。

**23. 什么是覆盖索引？它为什么能提升性能？**

- 覆盖索引：查询的列全部在索引中，**不需要回表** 。
- 提升性能：避免回表带来的随机 IO，减少磁盘访问 。

**24. 深分页 `LIMIT 1000000, 10` 为什么慢？怎么优化？**

- 慢的原因：需要扫描前 1000000 行并丢弃，只取最后 10 行。
- 优化方案：用**延迟关联**，先在索引上分页拿主键，再回表取数据：
  ```sql
  SELECT * FROM t JOIN (SELECT id FROM t LIMIT 1000000, 10) AS tmp ON t.id = tmp.id;
  ```
- 或者用 `WHERE id > 上次最大id LIMIT 10` 的方式。

**25. 一条 SQL 执行很慢，你的排查思路是什么？**

1. 用 `EXPLAIN` 看执行计划，检查 type、key、rows、Extra。
2. 检查是否命中索引，是否存在索引失效。
3. 检查表数据量、索引统计信息是否过期（`ANALYZE TABLE`）。
4. 检查是否有锁等待（`SHOW PROCESSLIST`、`INNODB STATUS`）。
5. 检查服务器资源（CPU、IO、内存）。


## 四、Java 基础与并发

**26. HashMap 的底层结构是什么？扩容机制是怎样的？**

- JDK 1.8：**数组 + 链表 + 红黑树**。链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树 。
- 扩容：负载因子默认 0.75，元素数超过 `容量 × 0.75` 时扩容为原来的 **2 倍**，重新分配元素 。

**27. HashMap 为什么线程不安全？ConcurrentHashMap 怎么保证线程安全？**

- **JDK 1.7**：扩容时头插法可能导致**环形链表**，造成死循环 。
- **JDK 1.8**：并发 put 可能发生**数据覆盖** 。
- **ConcurrentHashMap**：JDK 1.8 用 **CAS + synchronized** 锁单个哈希桶，锁粒度更细；扩容时多线程协同迁移 。

**28. synchronized 和 ReentrantLock 的区别是什么？**

- **synchronized**：JVM 层面实现，自动加锁释放，非公平，不可中断 。
- **ReentrantLock**：API 层面实现，需手动 `lock()/unlock()`，支持**公平锁**、**可中断**、**多个 Condition** 。

**29. volatile 的作用是什么？它保证原子性吗？**

- 作用：保证**可见性**和**禁止指令重排序** 。
- **不保证原子性**，如 `i++` 仍然不是原子操作 。

**30. ThreadLocal 的原理是什么？为什么会内存泄漏？怎么避免？**

- 原理：每个 `Thread` 有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 的**弱引用**，value 是强引用 。
- 泄漏原因：key 被 GC 回收后，value 仍被 Entry 强引用，无法回收 。
- 避免：使用后显式调用 `ThreadLocal.remove()` 。

**31. 线程池的核心参数有哪些？任务提交后的执行流程是什么？**

- 核心参数：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`handler` 。
- 流程：核心线程满 → 入队列 → 队列满 → 创建非核心线程 → 达到最大线程数 → 执行拒绝策略。

**32. 线程池的拒绝策略有哪些？**

- **AbortPolicy**：抛异常（默认）。
- **CallerRunsPolicy**：调用者线程执行。
- **DiscardPolicy**：直接丢弃。
- **DiscardOldestPolicy**：丢弃队列中最旧的任务，再尝试提交 。

**33. JMM 是什么？happens-before 原则了解吗？**

- JMM = Java Memory Model，定义多线程下共享变量的可见性和有序性规则。
- happens-before：如果 A happens-before B，则 A 的执行结果对 B 可见。例如：同一线程内程序顺序、锁的释放先于获取、volatile 写先于读 。

**34. CAS 是什么？ABA 问题怎么解决？**

- CAS = Compare And Swap，比较并交换，是乐观锁的核心原语。
- ABA 问题：值从 A 变成 B 又变回 A，CAS 误以为没变过 。
- 解决：加**版本号**（如 `AtomicStampedReference`）。

**35. AQS 的原理是什么？ReentrantLock 和 CountDownLatch 怎么基于它实现？**

- AQS = AbstractQueuedSynchronizer，用一个 `volatile int state` 表示同步状态，一个 **FIFO 等待队列** 管理阻塞线程 。
- ReentrantLock：state 表示重入次数，独占模式。
- CountDownLatch：state 表示计数，共享模式，计数到 0 唤醒所有等待线程 。


## 五、JVM

**36. JVM 内存区域怎么划分？哪些是线程私有的，哪些是共享的？**

- **线程私有**：程序计数器、虚拟机栈、本地方法栈 。
- **线程共享**：堆、方法区（元空间） 。

**37. 对象在堆上的分配过程是什么？什么时候会进入老年代？**

- 分配：优先在 **Eden 区**分配，Eden 满触发 Minor GC，存活对象进入 Survivor 区，年龄 +1。
- 进入老年代：年龄达到阈值（默认 15）、大对象直接进入、Survivor 空间不足时动态晋升。

**38. 垃圾回收算法有哪些？分代收集理论是什么？**

- 算法：**标记-清除**、**标记-复制**、**标记-整理** 。
- 分代：新生代用复制算法（对象朝生夕死），老年代用标记-清除或标记-整理（对象存活率高）。

**39. CMS 和 G1 的区别是什么？各自适用什么场景？**

- **CMS**：以最短停顿为目标，标记-清除，有内存碎片，适合老年代较大、对停顿敏感的场景。
- **G1**：分 Region，可预测停顿模型，标记-整理，无碎片，适合大堆（6GB+）。

**40. 什么情况会触发 Full GC？怎么排查频繁 Full GC？**

- 触发：老年代空间不足、元空间不足、显式调用 `System.gc()`、CMS 并发失败等。
- 排查：`jstat -gc` 看 GC 频率和耗时，`jmap -dump` 导出堆快照，用 MAT 分析对象占用。

**41. 类加载过程是什么？双亲委派模型的作用是什么？**

- 过程：加载 → 验证 → 准备 → 解析 → 初始化。
- 双亲委派：类加载请求先交给父加载器，父加载器无法完成才自己加载。作用：**保证核心类不被篡改**，避免重复加载。

**42. OOM 有哪些常见类型？怎么定位？**

- 类型：堆 OOM、栈 OOM、元空间 OOM、直接内存 OOM。
- 定位：`-XX:+HeapDumpOnOutOfMemoryError` 自动导出堆快照，用 MAT/JProfiler 分析。


## 六、Spring 与框架

**43. Spring Bean 的生命周期是什么？**

实例化 → 属性注入 → BeanNameAware/BeanFactoryAware → BeanPostProcessor 前置 → `@PostConstruct`/InitializingBean → BeanPostProcessor 后置 → 使用 → `@PreDestroy`/DisposableBean。

**44. Spring 怎么解决循环依赖？三级缓存分别存什么？**

- **一级缓存**：成品 Bean。
- **二级缓存**：半成品 Bean（已实例化未注入）。
- **三级缓存**：ObjectFactory，用于生成代理对象。
- 流程：A 实例化后放入三级缓存 → 注入 B 时从三级缓存拿到 A 的工厂生成代理 → B 完成 → A 完成。

**45. Spring AOP 的实现原理是什么？JDK 动态代理和 CGLIB 有什么区别？**

- 原理：动态代理，在目标方法前后织入增强逻辑。
- **JDK 动态代理**：基于接口，要求目标类实现接口。
- **CGLIB**：基于继承，生成子类，不能代理 final 类/方法。

**46. Spring 事务的传播行为有哪些？最常用的是哪几个？**

- 常用：`REQUIRED`（默认，有则加入，无则新建）、`REQUIRES_NEW`（总是新建）、`NESTED`（嵌套事务）、`SUPPORTS`、`NOT_SUPPORTED`。

**47. Spring 事务失效的常见场景有哪些？**

- 方法不是 public。
- 同类内部方法调用（未走代理）。
- 异常被 catch 未抛出。
- 异常类型不匹配 `rollbackFor`。
- 数据库引擎不支持事务（如 MyISAM）。

**48. MyBatis 中 `#{}` 和 `${}` 的区别是什么？**

- `#{}`：**预编译占位符**，防止 SQL 注入。
- `${}`：**字符串拼接**，直接替换，有 SQL 注入风险，仅用于表名、排序字段等动态场景。

**49. Spring Boot 自动装配的原理是什么？**

`@SpringBootApplication` → `@EnableAutoConfiguration` → `@Import(AutoConfigurationImportSelector)` → 读取 `META-INF/spring.factories`（或 2.7+ 的 `AutoConfiguration.imports`）→ 按条件装配 Bean。


## 七、Redis

**50. Redis 有哪些常用数据结构？分别适用什么场景？**

- **String**：缓存、计数器。
- **Hash**：对象存储。
- **List**：消息队列、最新列表。
- **Set**：去重、共同好友。
- **ZSet**：排行榜、延时队列。

**51. Redis 为什么快？**

纯内存操作、单线程避免锁竞争、IO 多路复用、高效数据结构。

**52. 缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么解决？**

- **穿透**：查不存在的数据。解决：布隆过滤器、空值缓存。
- **击穿**：热点 key 过期瞬间大量请求打到 DB。解决：互斥锁、逻辑过期。
- **雪崩**：大量 key 同时过期。解决：过期时间加随机值、多级缓存。

**53. Redis 的持久化机制 RDB 和 AOF 有什么区别？**

- **RDB**：快照，二进制，恢复快，可能丢数据。
- **AOF**：命令日志，实时性高，文件大，恢复慢。可配置 `appendfsync` 策略。

**54. Redis 过期删除策略和内存淘汰策略分别是什么？**

- 过期删除：**惰性删除 + 定期删除**。
- 内存淘汰：`noeviction`、`allkeys-lru`、`volatile-lru`、`allkeys-random`、`volatile-ttl` 等。

**55. 怎么用 Redis 实现分布式锁？有什么坑？**

- 方案：`SET key value NX PX timeout`，value 用唯一标识，释放时用 Lua 脚本校验。
- 坑：锁过期业务未完成、误删他人锁、Redis 主从切换锁丢失（可用 RedLock）。

**56. Redis 主从复制、哨兵、Cluster 分别解决什么问题？**

- **主从复制**：数据备份、读写分离。
- **哨兵**：主节点故障自动切换。
- **Cluster**：数据分片，水平扩展。


## 八、计算机网络与操作系统

**57. TCP 三次握手和四次挥手的过程是什么？**

- **三次握手**：SYN → SYN+ACK → ACK。
- **四次挥手**：FIN → ACK → FIN → ACK。

**58. 为什么握手是三次，挥手是四次？**

- 握手三次：确保双方收发能力都正常。
- 挥手四次：TCP 全双工，一方 FIN 后另一方可能还有数据要发，所以 ACK 和 FIN 分开发送。

**59. TCP 和 UDP 的区别是什么？**

TCP 面向连接、可靠、有序、有流量控制；UDP 无连接、不可靠、无序、开销小。

**60. HTTP 和 HTTPS 的区别是什么？HTTPS 握手过程了解吗？**

- HTTP 明文，HTTPS = HTTP + TLS/SSL，加密传输。
- HTTPS 握手：ClientHello → ServerHello + 证书 → 客户端验证 + 密钥交换 → 完成握手。

**61. 从输入 URL 到页面展示，中间发生了什么？**

DNS 解析 → TCP 连接 → 发送 HTTP 请求 → 服务器处理 → 返回响应 → 浏览器渲染 → 断开连接。

**62. 进程和线程的区别是什么？**

进程是资源分配的基本单位，线程是 CPU 调度的基本单位。进程间内存独立，线程共享进程内存。

**63. IO 多路复用是什么？select、poll、epoll 的区别是什么？**

- IO 多路复用：一个线程管理多个 IO 连接。
- **select**：有 FD 数量限制（1024），每次需要复制 FD 集合。
- **poll**：无数量限制，仍需遍历。
- **epoll**：事件驱动，无需遍历，适合高并发。


## 九、项目与场景题

**64. 你项目里最有挑战的一个点是什么？怎么解决的？**

结合自己的项目准备：说清**背景 → 难点 → 方案对比 → 最终选择 → 结果**。

**65. 项目里有没有用到缓存？缓存和数据库一致性怎么保证？**

- 方案：**Cache Aside**（先更新 DB，再删除缓存）+ 延迟双删 + 消息队列补偿。
- 强一致场景：分布式锁 + 读写串行化。

**66. 项目里有没有用到消息队列？怎么保证消息不丢失、不重复消费？**

- 不丢失：生产者确认 + Broker 持久化 + 消费者手动 ACK。
- 不重复：消费端幂等（唯一 ID + 去重表 / Redis setnx）。

**67. 如果线上接口突然变慢，你的排查思路是什么？**

监控告警 → 查看日志/链路追踪 → 检查 CPU/内存/IO/网络 → 检查 DB 慢查询 → 检查下游依赖 → 定位后回滚或限流。

**68. 如果数据库 CPU 飙高，你怎么定位问题？**

`SHOW PROCESSLIST` 看活跃 SQL → 慢查询日志 → `EXPLAIN` 分析 → 检查是否缺索引/锁等待/全表扫描。

**69. 设计一个秒杀系统，你会考虑哪些点？**

限流（网关层 + 应用层）、缓存预热、库存扣减（Redis + Lua）、异步下单（MQ）、防超卖、防刷、降级兜底。

**70. 分布式 ID 有哪些生成方案？雪花算法的原理是什么？**

- 方案：UUID、数据库自增、Redis INCR、雪花算法、美团 Leaf。
- 雪花算法：64 位 = 1 位符号 + 41 位时间戳 + 10 位机器 ID + 12 位序列号。
