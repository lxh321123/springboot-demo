# 1. Java 集合

## 1.1 HashMap 是什么

**大白话**：HashMap 就是一个"**查字典**"的工具。你给它一个 key（比如"张三"），它告诉你对应的 value（比如"20 岁"）。

**它底层怎么存的？**

```
数组 + 链表 + 红黑树
```

| 名词       | 大白话                           |
| ---------- | -------------------------------- |
| **数组**   | 一排格子，每个格子有编号（下标） |
| **链表**   | 一个格子连着一个格子，像铁链     |
| **红黑树** | 一种排好序的树，查找比链表快     |

**为什么要三种结构？**

- 数组：定位快，直接按下标找
- 但不同的 key 可能算到**同一个下标**（这叫**哈希冲突**）→ 用链表串起来
- 链表太长（≥8）查询就慢 → 转成红黑树，把 O(n) 变成 O(log n)

## 1.2 几个关键数字

**链表转红黑树的条件**：

```
链表长度 ≥ 8  且  数组长度 ≥ 64
```

如果链表到 8 了但数组还 < 64 → **先扩容，不树化**。

**为什么？** 数组太小，冲突本来就多，扩容比树化更划算。

**加载因子 0.75**：

```
存到 容量 × 0.75 就扩容
```

比如容量 16，存到 12 个就扩容成 32。

**为什么是 0.75？** 太大浪费空间，太小冲突多。0.75 是时间和空间的折中。

**为什么容量是 2 的幂？**

因为要算"这个 key 放哪个下标"，用 `(n-1) & hash` 代替 `hash % n`。

| 写法           | 速度         |
| -------------- | ------------ |
| `hash % n`     | 慢（除法）   |
| `hash & (n-1)` | 快（位运算） |

**前提**：n 必须是 2 的幂，这个等式才成立。

**hash 是什么？** key 经过"扰动函数" `h ^ (h >>> 16)` 算出来的一个数字。扰动是为了让哈希更分散，减少冲突。

## 1.3 put 流程（放一个 key-value）

```
① 算 hash，定位数组下标
② 该位置空 → 直接放
③ 该位置有值 → 链表尾插 / 树上插入
④ 超过 容量×0.75 → 扩容 2 倍
```

## 1.4 1.7 vs 1.8

|          | 1.7         | 1.8                  |
| -------- | ----------- | -------------------- |
| 插入方式 | **头插法**  | **尾插法**           |
| 结构     | 数组 + 链表 | 数组 + 链表 + 红黑树 |

**为什么从头插改尾插？**

1.7 头插法在**并发扩容**时可能让链表**成环**，导致死循环。1.8 改尾插 + 红黑树，既避免成环，又把长链表查询从 O(n) 降到 O(log n)。

## 1.5 ConcurrentHashMap

**大白话**：HashMap 的**线程安全版**。

**1.8 怎么保证安全？** **CAS + synchronized**，锁粒度是**每个桶的节点**，比 1.7 的分段锁更细。

| 名词             | 大白话                               |
| ---------------- | ------------------------------------ |
| **CAS**          | "比较再交换"，一种无锁的原子操作     |
| **synchronized** | Java 内置锁                          |
| **分段锁**       | 把锁分成几段，各锁各的（1.7 的做法） |

## 面试问题

1. **HashMap 底层结构？** 数组 + 链表 + 红黑树；链表 ≥8 且容量 ≥64 才树化，否则先扩容。
2. **为什么容量是 2 的幂？** 为了用 `(n-1) & hash` 代替取模，位运算更快。
3. **put 流程？** 算 hash 定位 → 空则放 → 有值则尾插/树插 → 超 0.75 扩容。
4. **1.7 和 1.8 区别？** 头插改尾插（防成环），引入红黑树（防长链表）。
5. **线程安全吗？** 不安全；ConcurrentHashMap 用 CAS + synchronized 保证。

# 2. 并发编程

## 2.1 多线程三问题

**大白话**：多个线程一起干活，会出三种乱子。

| 问题       | 大白话                                         | 解决办法                     |
| ---------- | ---------------------------------------------- | ---------------------------- |
| **原子性** | 一个操作被中途打断（`i++` 其实是读→加→写三步） | synchronized / AtomicInteger |
| **可见性** | 线程 A 改了值，线程 B 看不到（各自有缓存）     | volatile                     |
| **有序性** | 指令被重排，执行顺序乱了                       | volatile / synchronized      |

**`i++` 为什么不是原子的？**

```
i++ 看起来是一步，实际是三步：
  ① 读 i 的值
  ② 加 1
  ③ 写回去
```

中间任何一步被打断，结果就错了。

## 2.2 synchronized vs volatile

|          | synchronized             | volatile                                |
| -------- | ------------------------ | --------------------------------------- |
| 解决什么 | 原子性 + 可见性 + 有序性 | 只解决可见性 + 有序性，**不保证原子性** |
| 作用对象 | 方法 / 代码块            | 变量                                    |
| 性能     | 重                       | 轻                                      |

**关键**：

- `i++` 用 volatile **没用**（它不保证原子性）
- 状态标志位 `volatile boolean stop` **适合**用 volatile

**synchronized 原理**：锁升级

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
## 解释：
无锁
  │ 第一个线程访问
  ↓
偏向锁（记下线程 ID）
  │ 第二个线程来抢
  ↓
轻量级锁（CAS 自旋）
  │ 自旋多次失败
  ↓
重量级锁（操作系统阻塞）

## 场景：上厕所。

无锁：门开着，没人。

偏向锁：只有你一个人用，你进去把门虚掩，下次直接进。

轻量级锁：有几个人轮流用，谁先到谁进，其他人门口等一下（自旋）。

重量级锁：很多人抢，抢不到的去旁边椅子上睡（阻塞），等里面的人出来叫。
```

锁越来越重，因为竞争越来越激烈。

## 2.3 线程池

**大白话**：线程池就是"**一池子线程，反复用**"，不用每次都新建/销毁。

**7 个核心参数**，重点记 4 个：

| 参数              | 大白话                   |
| ----------------- | ------------------------ |
| `corePoolSize`    | 核心线程数（常驻）       |
| `maximumPoolSize` | 最大线程数               |
| `workQueue`       | 任务排队队列             |
| `handler`         | 拒绝策略（都满了怎么办） |

**执行流程（必背）**：

```
任务提交
  ↓ 核心线程没满？    → 创建核心线程执行
  ↓ 队列没满？        → 进队列排队
  ↓ 没到最大线程数？   → 创建临时线程执行
  ↓ 都满了           → 拒绝策略
```

**关键考点：先排队、后扩容。**

为什么不先创建临时线程？因为**创建线程有成本**。能排队就先排队，实在排不下才开临时线程。

**拒绝策略**：

| 策略                | 大白话     |
| ------------------- | ---------- |
| AbortPolicy（默认） | 抛异常     |
| CallerRunsPolicy    | 谁提交谁干 |
| DiscardPolicy       | 直接丢弃   |
| DiscardOldestPolicy | 丢最老的   |

**临时工生命周期**：队列满 → 创建并立刻干活 → 干完去队列抢活 → 超过 `keepAliveTime` 等不到活 → 退出。

**规约坑**：不允许用 `Executors` 创建线程池。因为 `newFixedThreadPool` 的队列**无界**，任务堆积会 OOM。要手动 `new ThreadPoolExecutor(...)`。

## 2.4 ThreadLocal

**大白话**：ThreadLocal 让**每个线程有自己独立的一份数据**，互不干扰。

**数据存在哪？**

**不存 ThreadLocal 对象里**，存在**当前线程自带的 ThreadLocalMap** 里，以 ThreadLocal 实例自身为 key。

**为什么能线程隔离？** 不同线程调同一个 ThreadLocal，各自写进自己的 map。

**内存泄漏问题**：

- key 是**弱引用**（外部没引用了，GC 就能回收）
- value 是**强引用**

**问题**：key 被回收后，留下 `(null, value)` 的**僵尸 Entry**，value 回收不掉。

**解决**：**必须在 `finally` 里 `remove()`**。

**强弱引用**：

|         | 强引用                 | 弱引用                         |
| ------- | ---------------------- | ------------------------------ |
| GC 态度 | 只要有人指着，绝不回收 | 只有弱引用指着，下次 GC 就回收 |
| 例子    | `User u = new User()`  | `WeakReference<>(...)`         |

四种引用：强、软（内存不够才回收）、弱、虚（了解名字）。

## 面试问题

1. **synchronized 和 volatile 区别？** 前者保证原子性+可见性+有序性；后者只保证可见性+有序性。
2. **`i++` 用 volatile 安全吗？** 不安全，因为 `i++` 是三步，volatile 不保证原子性；改用 AtomicInteger。
3. **线程池执行流程？** 核心 → 队列 → 临时 → 拒绝。
4. **为什么先排队再扩容？** 创建线程有成本，能排队就先排队。
5. **为什么不用 Executors？** 队列无界，任务堆积会 OOM。
6. **ThreadLocal 数据存哪？** 存在线程自带的 ThreadLocalMap，key 是 ThreadLocal 实例。
7. **为什么 key 用弱引用？** 让 ThreadLocal 对象能被回收；但会留下僵尸 Entry，必须 `remove()`。
8. **僵尸 Entry 怎么彻底解决？** `finally` 里 `remove()`。

## 一、模拟场景

**假设**：你的服务跑着跑着，报 OOM 了。

**日志**：

```
java.lang.OutOfMemoryError: Java heap space
```

**服务重启后，跑一段时间又 OOM。**

---

## 二、第 0 步：提前配置（关键）

**服务上线时**，启动参数里加：

```bash
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/ -jar app.jar
```

**作用**：**OOM 发生时，自动导出一份堆快照**。

**如果不加会怎样？** OOM 后**现场没了**，只能靠猜。

---

## 三、第 1 步：看对象直方图

**服务还在跑，你怀疑内存有问题**，用 `jmap -histo`。

**先查 pid**：

```bash
jps
# 输出：12345 app.jar
```

**然后**：

```bash
jmap -histo 12345
```

**输出**：

```
 num     #instances         #bytes  class name
   1:      15828400    1284324000  [B (byte[])           ← 1.28GB 全是 byte 数组
   2:       452000     336128000   com.example.OrderDTO  ← 336MB 订单对象
   3:       120000     96000000    java.lang.String
   4:       ...
```

**怎么读**：

- **第一名 `[B`（byte[]）**：占了 1.28GB，**异常大**
- **第二名 `OrderDTO`**：336MB，**业务对象异常多**

**判断**：**要么有大文件被读进内存，要么有大量订单对象没释放。**

---

## 四、第 2 步：导堆快照

**光看直方图不够**，得知道**"谁在引用这些对象"**。

**导快照**：

```bash
jmap -dump:live,format=b,file=/data/dump/a.hprof 12345
```

**注意**：

- **会触发 Full GC + STW**，服务会**暂停几秒到几十秒**
- **低峰期做**，或者摘流量后做
- **文件可能几 GB**，确保磁盘够

---

## 五、第 3 步：用 MAT 分析

**把 `a.hprof` 下载到本地**，用 **MAT（Memory Analyzer Tool）** 打开。

**MAT 是免费工具**，Eclipse 出的，下载就能用。

### 看什么

**① Dominator Tree（支配树）**

**看哪个对象"支配"了最多内存。**

```
OrderDTO 支配了 1.2GB
  ├─ OrderItem 300MB
  ├─ ...
```

**一眼看出**：**OrderDTO 是元凶。**

**② Leak Suspects（泄漏嫌疑）**

**MAT 自动分析最可能的泄漏点。**

```
Problem Suspect 1:
  One instance of "com.example.OrderCache" loaded by ...
  occupies 1.2GB (80% of heap)
```

**MAT 直接告诉你**：**`OrderCache` 占了 80% 内存。**

**③ Path to GC Roots（到 GC Roots 的路径）**

**从可疑对象反查"谁在引用它"。**

```
OrderCache
  ← static field "cache" in OrderService
  ← ...
```

**意思**：**`OrderService` 里有个静态字段 `cache`，一直引用着 `OrderCache`，没释放。**

**找到根因了！**

---

## 六、第 4 步：修代码

**看代码**：

```java
public class OrderService {
    private static Map<Long, Order> cache = new HashMap<>();   // ← 问题在这

    public Order getOrder(Long id) {
        if (!cache.containsKey(id)) {
            Order order = orderDao.query(id);
            cache.put(id, order);   // ← 只加不减，无限增长
        }
        return cache.get(id);
    }
}
```

**问题**：**`cache` 只加不减，无限增长**，最后 OOM。

**修法**：

- 用 **LRU 缓存**（如 `LinkedHashMap` 带容量限制）
- 或者用 **Redis** 做缓存，别放本地


## 3.1 内存结构（5 个区域）

**大白话**：JVM 把内存分成 5 块，有的共享、有的私有。

```
线程共享:
  堆 Heap        ★ 最大，new 的对象在这
  方法区/元空间   类信息、静态变量、常量

线程私有:
  虚拟机栈       方法调用、局部变量
  本地方法栈     native 方法
  程序计数器     记录执行位置
```

**关键**：**程序计数器是唯一不会 OOM 的区域**（必考）。

**OOM 是什么？** OutOfMemoryError，内存不够了。

| 区域     | 溢出报什么错                   |
| -------- | ------------------------------ |
| 堆       | `Java heap space`              |
| 元空间   | `Metaspace`                    |
| 虚拟机栈 | `StackOverflowError`（栈溢出） |

## 3.2 对象存活判断：可达性分析

**大白话**：从一组"根"出发，顺着引用找，找不到的就是垃圾。

**GC Roots（根）有哪些？**

```
① 栈里的局部变量
② 静态变量
③ 常量
④ native 方法引用
```

**为什么不用引用计数法？** 因为对象互相引用时，计数永远不为 0，回收不掉。

## 3.3 分代回收（对象的一生）

```
1. new → 进 Eden
2. Eden 满 → Minor GC → 幸存者进 Survivor，年龄+1
3. 每次 Minor GC 幸存 → 年龄+1
4. 年龄到 15（默认）→ 晋升老年代
5. 老年代满 → Full GC（整个堆，STW 长）
```

**Eden : S0 : S1 = 8 : 1 : 1**

好，这个问题问到点子上了。**两个 Survivor 是为了配合"复制算法"。**

---

## 一、先看复制算法怎么工作

**复制算法需要"两块空间"**：

```
一块在用（放数据），一块空着（备用）
回收时：把活的复制到空的那块，然后清空原来那块
```

**为什么需要两块？** 因为**复制要有目标**。你不能往自己身上复制。

---

## 二、如果只有一个 Survivor 会怎样

**假设**：Eden + 1 个 Survivor。

**Minor GC 时**：

```
Eden 满了 → 把 Eden 里活的复制到 Survivor
→ 复制完，清空 Eden
```

**下一次 Minor GC**：

```
Eden 又满了 → 要把 Eden 和 Survivor 里活的，复制到哪？
→ Survivor 自己还在用，没法复制到自己身上
→ 没地方放
```

**问题**：**只有一块 Survivor，第二次 GC 就没地方复制了。**

---

## 三、两个 Survivor 怎么解决

**两块 Survivor，轮流当"目标"。**

**第一次 Minor GC**：

```
Eden 和 S0 里活的 → 复制到 S1
→ 清空 Eden 和 S0
```

**第二次 Minor GC**：

```
Eden 和 S1 里活的 → 复制到 S0
→ 清空 Eden 和 S1
```

**效果**：**总有一块 Survivor 是空的，可以当复制目标。**

---

## 四、用生活比喻

**场景**：整理书架。

**一个书架**：书满了，想整理，**没地方放**。

**两个书架**：

- 书架 A 有书，书架 B 空着
- 整理时：**把 A 里要留的书，搬到 B**
- 然后清空 A
- 下次整理：**把 B 里要留的书，搬到 A**

**两个书架轮流用，总有一个是空的。**

---

## 五、为什么是 8:1:1

**Eden 大，Survivor 小，因为**：

- **大部分对象在 Eden 就死了** → Eden 要大
- **存活下来的少** → Survivor 不需要大

**8:1:1 的含义**：

```
新生代总共 10 份
Eden 占 8 份
S0 占 1 份
S1 占 1 份
```

**为什么 Survivor 只占 1 份？**

因为**一次 Minor GC 后，存活的对象大约只占 10%**，1 份 Survivor 够放。

**大白话**：**Eden 是"大产房"，Survivor 是"小中转站"，够用就行。**

---

## 六、一句话总结

> **两个 Survivor 是为了配合复制算法。**
> **复制需要"一块在用、一块空着"。**
> **只有一个 Survivor，第二次 GC 就没地方复制了。**
> **两个轮流用，总有一个空的。**
> **Eden 大、Survivor 小，因为大部分对象在 Eden 就死了。**

---

现在应该清楚了。如果还有哪个点（比如"为什么是 8:1:1 不是 7:1:1"）想深入，直接说。

**为什么这么分？** 因为一次 Minor GC 后约 98% 对象死亡，两个 Survivor 留一块用来复制。

**复制算法**：只搬活人，搬完原地整体清空 → 无碎片；牺牲一块空间（10%）。

**为什么新生代用复制、老年代用标记-整理？**

|        | 新生代                       | 老年代                                      |
| ------ | ---------------------------- | ------------------------------------------- |
| 存活率 | 低（大部分死）               | 高（大部分活）                              |
| 算法   | 复制（搬活人成本低：活人少） | 标记-整理（搬活人成本高：活人多，不如整理） |

**Minor GC vs Full GC**：

|      | Minor GC   | Full GC                |
| ---- | ---------- | ---------------------- |
| 范围 | 只扫新生代 | 整堆                   |
| 速度 | 快         | 慢，STW 长             |
| 触发 | Eden 满    | 老年代满 / System.gc() |

**晋升老年代规则**：

1. 大对象直接进（如大数组）
2. 动态年龄判断
3. Survivor 装不下直接进

## 3.4 垃圾回收器

**STW** = Stop The World，GC 时暂停所有业务线程。

**回收器进化 = 压缩 STW 的历史**：

| 回收器   | 特点                 |
| -------- | -------------------- |
| Serial   | 单线程               |
| Parallel | 多线程，重吞吐       |
| CMS      | 并发、短停顿、已废弃 |
| **G1**   | JDK9+ 默认           |
| ZGC      | 停顿 <1ms            |

**G1**：

- 不物理分代，把堆切成**等大 Region**（1~32MB）
- 每个 Region 动态扮演 Eden/Old 角色
- 回收时**优先回收垃圾占比最高的 Region**，实现可预测停顿（默认 200ms）
- 适合大内存、多核机器

## 3.5 OOM 排查四步

```
① 内存现场：启动参数加 -XX:+HeapDumpOnOutOfMemoryError
② jmap -histo <pid>   → 看对象直方图，哪个类最多
③ jmap -dump / MAT 分析 .hprof → 看支配树，找"谁拽着对象不放"
④ 修代码：无限增长的集合 / 连接没关 / 缓存无上限 / ThreadLocal 没 remove
```

**常用命令**：

- `jstat -gcutil <pid> 1000` 看 GC 频率
- `jmap -dump:live,format=b,file=a.hprof <pid>` 手动导堆

## 面试问题

1. **JVM 内存区域？** 堆、方法区（共享）；虚拟机栈、本地方法栈、程序计数器（私有）。
2. **哪个不会 OOM？** 程序计数器。
3. **栈溢出和堆溢出？** 栈报 StackOverflowError，堆报 Java heap space。
4. **对象存活判断？** 可达性分析，从 GC Roots 出发。
5. **为什么不用引用计数？** 循环引用回收不掉。
6. **对象一生？** Eden → Minor GC → Survivor 来回复制、年龄+1 → 15 岁晋升 → 老年代 Full GC。
7. **Minor GC 和 Full GC 区别？** 前者只扫新生代、快；后者整堆、慢、STW 长。
8. **为什么新生代复制、老年代标记-整理？** 新生代存活率低，复制成本低；老年代存活率高，复制亏损。
9. **G1 特点？** Region 划分、优先回收垃圾多的、可预测停顿。
10. **OOM 排查？** jmap -histo 看直方图 → dump + MAT 找引用链 → 修代码。

# 4. Spring

## 4.1 IOC / DI

**大白话**：对象创建权从"你 new"反转给"容器"。

```java
// 传统：自己 new
OrderDao dao = new OrderDao();

// Spring：容器创建并注入
@Service
public class OrderService {
    @Autowired
    private OrderDao orderDao;
}
```

| 名词           | 大白话                       |
| -------------- | ---------------------------- |
| **IOC**        | 控制反转，创建权从你转给容器 |
| **DI**         | 依赖注入，容器把对象塞给你   |
| **Bean**       | 容器管理的对象               |
| **@Autowired** | "这里帮我注入"               |

**注入方式**：构造器注入（推荐）、Setter 注入、字段注入。

## 4.2 AOP

**大白话**：把公共逻辑（日志/事务/权限）抽出来，自动套到很多方法上。

**四个概念**：

| 名词                 | 大白话       |
| -------------------- | ------------ |
| **切点 Pointcut**    | 在哪套       |
| **通知 Advice**      | 套什么       |
| **切面 Aspect**      | 切点 + 通知  |
| **连接点 JoinPoint** | 所有候选方法 |

**动态代理**：

|            | JDK            | CGLIB                  |
| ---------- | -------------- | ---------------------- |
| 能代理什么 | 实现了接口的类 | 没实现接口的类         |
| 怎么生成   | 生成接口代理类 | 生成目标类的子类       |
| 限制       | 必须有接口     | 不能代理 final 方法/类 |

**Spring 默认**：实现了接口用 JDK，否则用 CGLIB。

## 4.3 Bean 生命周期

```
实例化(构造) → 属性填充(IOC)
  → @PostConstruct (初始化)
  → BeanPostProcessor 前后处理
  → 使用
  → @PreDestroy (销毁)
```

**三个钩子**：**构造 → @PostConstruct → @PreDestroy**。

**Bean 默认单例**，容器启动时（非懒加载）创建。

## 4.4 Spring 事务失效 8 场景 ★必背

**核心原理**：Spring 事务基于**动态代理**，只有经过代理调用才被增强。

```
1. 自调用(this.save())        → 不走代理
2. 方法不是 public            → 代理贴不上
3. 加在 private/final/static  → 代理无法覆盖
4. 没被 Spring 管理(不是 Bean)
5. 异常被 try-catch 吞掉      → 事务器认为成功
6. 抛受检异常未配置 rollbackFor → 默认只回滚 RuntimeException
7. 回滚后又捕获抛掉
8. 传播行为设置错
```

**自调用为什么失效？** `this.save()` 绕过代理，切面没机会拦截 → 事务没开。**本质两个字：代理。**

## 面试问题

1. **IOC 和 DI 关系？** IOC 是思想，DI 是实现方式。
2. **AOP 四个概念？** 切点、通知、切面、连接点。
3. **AOP 默认用哪个代理？** 取决于 Bean 有没有实现接口。
4. **JDK 和 CGLIB 区别？** JDK 要接口，CGLIB 靠继承（不能 final）。
5. **Bean 生命周期？** 构造 → @PostConstruct → @PreDestroy。
6. **事务为什么失效？** 基于动态代理，绕过代理或吞异常就失效。
7. **自调用本质原因？** 代理。
8. **受检异常会回滚吗？** 默认不会，要配 `rollbackFor`。

# 5. MySQL

## 5.1 为什么用 B+ 树

**大白话**：索引要解决的是"**百万行数据里，怎么用最少的磁盘 IO 找到那一行**"。

**磁盘 IO 很慢**（机械盘一次约 10ms），**树的高度 = IO 次数**，所以要把树压矮。

| 结构      | 为什么不行                                                   |
| --------- | ------------------------------------------------------------ |
| 红黑树    | 数据多时太高（20 层 = 20 次 IO）                             |
| 哈希      | 只支持等值，**范围查询全废**                                 |
| B 树      | 所有节点存数据，单页放不下更多指针，树变高                   |
| **B+ 树** | 非叶子只存索引（扇出大，**3 层约 2000 万行**）；叶子双向链表，**范围查询飞快** |

**为什么单表建议 < 2000 万行？** 3 层是估算上限，超过树变 4 层，多一次 IO。

## 5.2 聚簇索引 vs 二级索引

```
主键索引(聚簇): 叶子节点 = 整行数据
普通索引(二级): 叶子节点 = 索引列 + 主键值
```

**回表**：用二级索引查到主键后，再去聚簇索引查整行。

**覆盖索引**：索引里已经包含查询所需字段，**不用回表，更快**。

**`SELECT *` 的问题**：可能无法覆盖索引导致回表，所以只查需要的字段。

## 5.3 最左前缀

**大白话**：联合索引按第一列排，第一列相等再按第二列排。

```
INDEX(name, age)
  WHERE name=...        ✅
  WHERE name AND age    ✅
  WHERE age             ❌（跳过 name）
```

**范围条件会断档**：`WHERE name='张' AND age>18`，age 只能过滤，后面的列索引失效。

**口诀**：**最左不能跳，等值可乱序，范围会断档，范围放最后。**

## 5.4 索引失效 6 大场景 ★必背

```
1. 对索引列做函数/运算      → date(create_time)=...  ❌
2. 隐式类型转换             → WHERE name=123 ❌
3. 前导模糊查询             → LIKE '%张'  ❌
4. 范围条件后面的列           → 断档
5. != / NOT IN / OR 非索引列  → 失效
6. 联合索引违背最左前缀        → 失效
```

**口诀**：**函数、类型、前置%、范围后、or/!=，联合最左不能破。**

## 5.5 事务 ACID

| 特性   | 靠什么实现                       |
| ------ | -------------------------------- |
| 原子性 | undo log（记录修改前，回滚）     |
| 一致性 | 由其他三个共同保证（总目标）     |
| 隔离性 | MVCC + 锁                        |
| 持久性 | redo log（记录修改后，崩溃恢复） |

## 5.6 隔离级别

**三大并发问题**：

| 问题           | 大白话                           |
| -------------- | -------------------------------- |
| **脏读**       | 读到未提交的数据                 |
| **不可重复读** | 两次读同一行，结果不同（UPDATE） |
| **幻读**       | 两次按条件查，多出数据（INSERT） |

**级别**：读未提交 / 读已提交 RC / **可重复读 RR（InnoDB 默认）** / 串行化。

**RR 下**：快照读靠 **MVCC**（基本无幻读），当前读靠**间隙锁**（防幻读）。

## 5.7 MVCC

**大白话**：**读不阻塞写、写不阻塞读**，靠给数据保留多个历史版本。

**实现**：

- 每行隐藏字段 `DB_TRX_ID`（最后修改事务 ID）+ `DB_ROLL_PTR`（指向 undo log 旧版本，串成版本链）
- **ReadView**（快照）：记录当前活跃事务，沿版本链找回"可见的版本"

**RC vs RR 的区别**：

|      | ReadView 生成时机        |
| ---- | ------------------------ |
| RC   | 每次查询都生成新的       |
| RR   | 只在第一次查询生成并复用 |

**就这一条区别**，决定了 RR 可重复读。

## 5.8 锁

| 锁                   | 锁什么                             |
| -------------------- | ---------------------------------- |
| 行锁 Record Lock     | 某一行                             |
| 间隙锁 Gap Lock      | 两记录间空隙（RR 防幻读靠它）      |
| 临键锁 Next-Key Lock | 行锁 + 间隙锁（RR 当前读默认单位） |

## 5.9 explain

| 列     | 重点                                                  |
| ------ | ----------------------------------------------------- |
| `type` | const > ref > range > index > **ALL**（ALL = 全表扫） |
| `key`  | 实际用的索引，空 = 没走                               |
| `rows` | 预估扫描行数，越少越好                                |

## 5.10 主键设计

| 方案     | 结论                               |
| -------- | ---------------------------------- |
| 自增主键 | ✅ 常规用，顺序追加**不触发页分裂** |
| 雪花/ID  | 分布式/对外用，随机插入会页分裂    |
| 业务字段 | ❌ 不推荐（可能变、过大）           |

**为什么自增快？** 新数据总是追加到最后，不折腾；随机主键插到中间，页满了要**页分裂**。

## 5.11 联合索引排序规则

- **等值列放前面，范围列放后面**
- 例：`WHERE create_time BETWEEN ... AND status=1`，索引应建 `(status, create_time)`

## 面试问题

1. **为什么用 B+ 树？** 非叶子只存索引、扇出大、树矮 IO 少；叶子双向链表，范围查询快。
2. **B+ 树多少层存多少？** 3 层约 2000 万行；超过变 4 层多一次 IO。
3. **聚簇 vs 二级索引？** 前者叶子存整行，后者叶子存索引列+主键。
4. **什么是回表？** 二级索引查到主键后，再回聚簇索引查整行。
5. **什么是覆盖索引？** 索引里已含查询所需字段，不用回表。
6. **最左前缀？** 联合索引从最左列开始用，不能跳。
7. **索引失效场景？** 函数、类型、前置%、范围后、or/!=、违背最左。
8. **ACID 靠什么？** 原子性 undo log，持久性 redo log，隔离性 MVCC+锁。
9. **脏读/不可重复读/幻读？** 读到未提交 / 同行变了 / 多出行。
10. **InnoDB 默认级别？** RR，靠 MVCC 实现可重复读。
11. **RC 和 RR 区别？** ReadView 生成时机：每次 vs 只一次。
12. **间隙锁干什么？** RR 当前读时锁住空隙，防幻读。
13. **explain 怎么看？** type=ALL 全表扫，key 空没走索引，rows 越少越好。
14. **自增主键为什么减少页分裂？** 顺序追加，不插中间。

# 6. Redis

## 6.1 缓存三兄弟 ★必考

**先建立场景**：Redis 是挡在 MySQL 前面的缓存，读请求先查 Redis，没有才查 MySQL 并回填。

### ① 缓存穿透

**大白话**：查一个**根本不存在**的数据（如 id=-1），每次请求都穿过 Redis 打到 MySQL。

**方案**：

| 方案           | 大白话                                         |
| -------------- | ---------------------------------------------- |
| 缓存空值       | 没有也存个 null + 短过期                       |
| **布隆过滤器** | 一个超大的位数组，能判断"肯定不存在"，拦在入口 |
| 参数校验       | 非法 id 直接拒绝                               |

**一句话**：穿透 = 问一个"就是不存在的"，防护 = 挡在入口或缓存空值。

### ② 缓存击穿

**大白话**：某个**热 key 突然过期**，一瞬间大量请求打到 MySQL。

**方案**：

| 方案       | 大白话                                   |
| ---------- | ---------------------------------------- |
| **互斥锁** | 只让一个线程去查库重建，其他等           |
| 逻辑过期   | key 永不过期，value 存过期时间，异步重建 |
| 热点预热   | 提前加载                                 |

**一句话**：击穿 = 一个热 key 过期瞬间被打穿，防护 = 让重建串行化或根本不消失。

### ③ 缓存雪崩

**大白话**：**大量 key 同一时刻过期**（或 Redis 宕机），请求全压到 MySQL。

**方案**：

| 方案                 | 大白话       |
| -------------------- | ------------ |
| **过期时间加随机值** | 错开过期时刻 |
| 多级缓存             | 本地 + Redis |
| 集群高可用           | 哨兵/集群    |
| 熔断限流降级         | 保护 DB      |

**一句话**：雪崩 = 大面积 key 同时失效，防护 = 错开过期时间 + 避免单点。

### 三兄弟对比

|      | 穿透       | 击穿            | 雪崩                   |
| ---- | ---------- | --------------- | ---------------------- |
| 数据 | 根本不存在 | 一个热 key 过期 | 大量 key 同刻过期      |
| 规模 | 单个/任意  | 单个热点        | 大面积                 |
| 方案 | 布隆/空值  | 互斥锁/逻辑过期 | 随机过期/多级缓存/集群 |

## 6.2 持久化 RDB vs AOF

**大白话**：持久化 = 把内存数据存到磁盘，防重启丢数据。

|      | RDB 快照           | AOF 命令日志   |
| ---- | ------------------ | -------------- |
| 原理 | 周期 dump 整个内存 | 追加每条写命令 |
| 比喻 | 定期拍照           | 记流水账       |
| 优点 | 文件小、恢复快     | 丢失少         |
| 缺点 | 快照间隙数据丢失   | 文件大、重放慢 |

**AOF 刷盘策略**：

| 策略             | 丢多少     |
| ---------------- | ---------- |
| always           | 不丢，最慢 |
| everysec（默认） | 丢 1 秒    |
| no               | 不确定     |

**混合持久化（4.0+）**：AOF 重写时把当前快照 RDB 存进 AOF 头，再追加增量 → 恢复快 + 丢得少。

## 6.3 分布式锁

**大白话**：多台服务器同时操作共享资源（如扣库存），本地锁管不着别人，需要跨进程的锁。

**三要求**：① 互斥 ② 持有者挂了能释放 ③ 只能释放自己的锁。

**加锁**：

```
SET lock "userId" NX EX 10
```

**必须一个原子命令**（不能 setnx 再 expire，两步中间崩了死锁）。value 存唯一标识，证明是自己的锁。

**解锁（Lua）**：

```lua
if redis.call('get','lock') == 'userId' then
    return redis.call('del','lock')
else return 0 end
```

**两大坑**：

1. **锁过期但业务没做完** → 看门狗机制（Redisson watchDog，定期续期）
2. **释放别人的锁** → value 唯一标识 + Lua 校验

**结论**：用 Redisson（原子加锁 + 看门狗续期 + Lua 解锁 + RedLock）。

## 面试问题

1. **缓存三兄弟？** 穿透（不存在）、击穿（一个热 key 过期）、雪崩（大量 key 同刻过期）。
2. **穿透怎么解决？** 缓存空值、布隆过滤器、参数校验。
3. **击穿怎么解决？** 互斥锁、逻辑过期、预热。
4. **雪崩怎么解决？** 随机过期、多级缓存、集群。
5. **RDB 和 AOF 区别？** RDB 快照恢复快但丢多；AOF 命令日志丢少但恢复慢。
6. **AOF 刷盘策略？** always / everysec（默认，丢 1 秒）/ no。
7. **混合持久化？** AOF 头放 RDB 快照，后面放增量命令。
8. **分布式锁怎么加？** `SET NX EX` 原子命令，value 存唯一标识。
9. **为什么用 Lua 解锁？** 保证"判断是我的 + 删除"原子。
10. **锁过期业务没做完？** 看门狗自动续期。
11. **为什么不直接用 setnx？** 没过期会死锁；两步中间崩了锁不释放；不校验会删别人锁。
